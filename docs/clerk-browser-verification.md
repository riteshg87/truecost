# Clerk development browser verification

This report records the bounded development browser check for the custom TrueCost email OTP flow. It uses the repository's bundled Playwright runtime and an isolated Chrome context for each synthetic account. It does not claim real email delivery or production readiness.

## Procedure

- Start from a completed production build and run `node scripts/check-clerk-browser.mjs` with an explicitly free owned port, for example `TRUECOST_CLERK_BROWSER_PORT=4317`.
- The script reads the ignored development `.env.local` values without printing them. It requires the approved `pk_test`/`sk_test` pair, the expected development issuer, and the approved development Convex target before making any API call.
- A short-lived Clerk Testing Token is created through `POST https://api.clerk.com/v1/testing_tokens` when `CLERK_TESTING_TOKEN` is not already supplied. The official `@clerk/testing/playwright` helper (pinned at `2.2.36`) routes only the exact approved Frontend API and applies Clerk's documented testing response handling, including its CAPTCHA bypass state. It is never logged or written to evidence. Playwright `1.62.1` is pinned as the helper's development peer; Cypress is not installed.
- Each account uses a fresh browser context. The approved development test addresses use Clerk's documented `+clerk_test` convention and code `424242`; no email is sent.
- The harness does not automate CAPTCHA interaction. If Clerk presents a challenge, the run records the unresolved challenge and stops for a permitted manual check.
- The check enters an invalid six-digit code first, confirms a safe recoverable error, then verifies with `424242`, opens Account, confirms the current synthetic address is shown and the other address is absent, signs out, and repeats with the second account.
- After both existing-account checks pass, a third fresh context generates a unique `truecost-browser-<uuid>+clerk_test@example.com` address, confirms through the Clerk API that it is absent, and exercises creation through the UI only. The owned disposable account is revoked and removed during cleanup when it was created by this run; existing synthetic accounts are never deleted.
- Set `TRUECOST_BROWSER_LOAN_CHECK=1` to extend only that newly-created signup context with a fixed-basis synthetic loan check. It saves the ₹18,00,000 / ₹20,00,000 record, reloads Loan and a transfer quote, queues a 7.8% edit while offline, then reconnects and confirms the server acknowledgement before reload. It also checks that a cold offline reload does not expose the private lender, confirms the record returns after reconnect, captures 390px and 320px Account/Loan views, checks overflow and full email visibility, tests keyboard focus and the sign-out warning, and deletes the loan through Account before final sign-out.

## Limits

This is a development-instance browser check. It does not verify delivery to a real mailbox, production custom-domain settings, provider dashboard policy, private comparison operations, service-worker privacy behavior, or any cloud deployment. Saved-loan behavior is covered only when the opt-in `TRUECOST_BROWSER_LOAN_CHECK=1` extension is run on a fresh completed build. Clerk cleanup removes only a newly created disposable identity and its sessions. The current backend has no identity deletion or tombstone operation, so a Convex profile created during signup may remain and is reported as such in the machine record. Any failed UI phase is recorded with a redacted message and should be fixed in the auth slice rather than worked around in this script.
